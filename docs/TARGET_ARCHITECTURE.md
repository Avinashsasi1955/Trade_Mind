**Date**: 2026-10-12  
**Status**: Target Design Specification  
**System**: `Trade_Mind` Private Autonomous Trading System

---

## 1. Architectural Principles

1. **Single Source of Truth**: Eliminate the SQLite / PostgreSQL split. PostgreSQL is the sole runtime database for all market data, orders, fills, positions, and portfolio accounting. SQLite is relegated strictly to ephemeral offline unit tests.
2. **Deterministic Risk Invariance**: No trade proposal—whether generated by quantitative models, technical rules, or AI agents—can bypass the deterministic risk engine.
3. **Decoupled Interfaces**: Abstract boundaries decouple market-data ingestion and broker execution. Transitioning from Upstox data to Zerodha execution requires zero modifications to strategy, risk, or portfolio accounting modules.
4. **Data Provenance Transparency**: Every price tick, candle, and quote carries an explicit provenance tag (`LIVE_STREAM`, `REST_BACKFILL`, `HISTORICAL_BHAVCOPY`, or `SYNTHETIC_FIXTURE`). Synthetic prices are never silently substituted for live market data.
5. **Capital Preservation & Idempotency**: Virtual trading starts with ₹10,00,000. Double-entry accounting ensures cash, margin, and fees are persisted across system restarts without double counting. Order creation and reconciliation are strictly idempotent.

## 3. Detailed Component Specifications

### 3.1 Market-Data Layer & Data Provenance
- **Provider Interface**:
  ```python
  class MarketDataFeed(ABC):
      @abstractmethod
      def connect(self) -> None: ...
      @abstractmethod
      def subscribe(self, symbols: List[str], mode: str) -> None: ...
      @abstractmethod
      def on_tick(self, tick: TickData) -> None: ...
  ```
- **Provenance Taxonomy**:
  - `LIVE_STREAM`: Verified real-time WebSocket tick from provider (Upstox Protobuf / Kite binary).
  - `REST_BACKFILL`: Historical 1m/5m intraday candle retrieved from official provider REST API.
  - `HISTORICAL_BHAVCOPY`: End-of-day official exchange daily data with SHA-256 provenance checksum.
  - `SYNTHETIC_FIXTURE`: Offline deterministic mock data used solely in local test runs. Must be displayed with a red "SIMULATED / SYNTHETIC" banner on the frontend.

### 3.2 Canonical Paper Portfolio & Accounting Engine (Zero Double-Counting)

To prevent accounting distortion and ensure financial integrity, all portfolio balances adhere to standard Indian clearinghouse accounting conventions:

#### A. Core Balances & Definitions
1. **Starting Virtual Capital ($E_0$)**: Exactly ₹10,00,000.00 virtual cash balance recorded upon account initialization.
2. **Total Cash Balance ($\text{Cash}$)**: The liquid unencumbered currency in the account.
   $$\text{Cash Balance} = E_0 + \sum \text{Realized P\&L} - \sum \text{Transaction Costs Paid} - \sum \text{Cash Outlay on Delivery Equities}$$
   *(When cash-equity shares are bought for delivery, actual cash decreases by the purchase price plus fees).*
3. **Current Market Value of Cash Holdings ($V_{\text{holdings}}$)**:
   $$V_{\text{holdings}} = \sum_{i \in \text{Delivery Holdings}} \left( \text{Quantity}_i \times \text{Current Market Price}_i \right)$$
4. **Blocked Margin ($M_{\text{blocked}}$)**: Collateral earmarked from the cash balance to back open leveraged positions (intraday MIS equity, futures, or option write requirements).
   $$M_{\text{blocked}} = \sum_{j \in \text{Margin Positions}} \text{Margin Requirement}_j$$
   > [!IMPORTANT]
   > **No Double-Counting Invariant**: Blocked margin is an allocation of the existing Cash Balance, **NOT** an independent asset. It must never be added to Cash or counted as additional equity.
5. **Available Funds / Free Cash ($\text{Funds}_{\text{available}}$)**: Capital available to initiate new trades:
   $$\text{Funds}_{\text{available}} = \text{Cash Balance} - M_{\text{blocked}} + \min\left(0, \sum \text{Unrealized P\&L}_{\text{margin}}\right)$$
   *(Conservative rule: Unrealized gains on open margin trades do not expand intraday buying power until closed; unrealized losses directly reduce buying power).*
6. **Total Portfolio Equity ($E_{\text{total}}$)**: True liquidation value of the portfolio:
   $$E_{\text{total}} = \text{Cash Balance} + V_{\text{holdings}} + \sum \text{Unrealized P\&L}_{\text{margin}}$$
   *Equivalent verification formula*:
   $$E_{\text{total}} = E_0 + \sum \text{Realized P\&L} + \sum \text{Unrealized P\&L}_{\text{all}} - \sum \text{Transaction Costs Paid}$$

#### B. Reconciliation Invariants & Tests
- **Daily Double-Entry Audit**: On every order fill, fee debit, and trade exit, an automated audit verifies:
  $$\left| E_{\text{total}} - \left( E_0 + \sum \text{Realized P\&L} + \sum \text{Unrealized P\&L} - \sum \text{Costs} \right) \right| \le ₹0.01$$
- **Persistence Across Restarts**: On service restart, the portfolio engine reloads the exact cash journal, open holdings, and blocked margin records from PostgreSQL without resetting equity to ₹10,00,000.00.

### 3.3 Independent Pre-Trade Risk Engine & Proportional Sizing
- **Position Sizing Formula**:
  $$\text{Risk Budget} = E_{\text{total}} \times 0.0025 = ₹2,500.00 \quad (\text{at } E_{\text{total}} = ₹10,00,000)$$
  $$\text{Stop Distance} = |\text{Entry Price} - \text{Stop Loss Price}|$$
  $$\text{Quantity} = \min\left( \left\lfloor \frac{\text{Risk Budget}}{\text{Stop Distance}} \right\rfloor, \left\lfloor \frac{\text{Funds}_{\text{available}} \times 0.20}{\text{Entry Price}} \right\rfloor \right)$$
  - Orders are rejected if $\text{Stop Distance} = 0$, if $\text{Quantity} < 1$, or if total order value exceeds ₹2,00,000 (20% single-stock position limit).
- **Session Circuit Breakers**:
  - **Daily Realized + Unrealized Loss $\ge ₹10,000$ (1.0%)**: Blocks all new entry orders for the remainder of the session. Alerts operator.
  - **Account Drawdown $\ge 3.0\%$ (₹30,000)**: Warning alert raised; maximum concurrent positions halved.
  - **Emergency Shutdown $\ge 5.0\%$ (₹50,000)**: System halts all strategy evaluations; triggers safe exit protocol.
  - **Hard SQL Stop**: -7.32% database trigger locks database from processing further fills.

### 3.4 Order & Execution State Machine
Every order transitions through an auditable, persistent state machine:

```
[PROPOSED] ──► [RISK_EVALUATION]
                     │
         ┌───────────┴───────────┐
         ▼                       ▼
  [RISK_REJECTED]           [APPROVED]
                                 │
                                 ▼
                     [SUBMITTED_TO_SIMULATOR]
                                 │
                     ┌───────────┴───────────┐
                     ▼                       ▼
                  [FILLED]          [REJECTED_BY_SIM]
                     │
                     ▼
             [OPEN_IN_POSITION]
                     │
                     ▼
               [EXIT_PENDING]
                     │
                     ▼
                  [CLOSED]
```

- **Idempotency**: All order requests require a unique, client-generated UUID (`client_order_id`). Duplicate submissions return the existing order record without opening duplicate exposure.
- **Partial Fills**: Simulator tracks `filled_quantity` and `remaining_quantity`. Unfilled balances are cancelled after timeout.

### 3.5 Derivatives Architecture (Futures & Options)
- **Staged Rollout**: Cash equities are validated first. Derivatives are introduced only after the core cash engine passes comprehensive paper-trading criteria.
- **Futures Engine**:
  - Notional value: $\text{Quantity} \times \text{Futures Price} \times \text{Lot Size}$.
  - Margin requirement: Official exchange initial margin + exposure margin modeling.
  - Daily mark-to-market (MTM) settlement and gap-risk buffer.
- **Options Engine**:
  - Greeks calculation (Delta, Gamma, Theta, Vega) and real-time IV tracking.
  - Strike step and contract expiry validation against official exchange masters.
  - Strict classification: Defined-risk (e.g. Long Calls, Long Puts, Spreads) vs. Undefined-risk (Naked short options are strictly prohibited).
  - Minimum liquidity filter: Bid-ask spread $\le 2.5\%$ of premium; minimum contract open interest $\ge 500$ contracts.

### 3.6 Broker Boundary & Future Zerodha Migration
- **Abstract Execution Interface**:
  ```python
  class ExecutionBroker(ABC):
      @abstractmethod
      def place_order(self, order: OrderRequest) -> OrderResponse: ...
      @abstractmethod
      def cancel_order(self, order_id: str) -> bool: ...
      @abstractmethod
      def fetch_positions(self) -> List[PositionRecord]: ...
      @abstractmethod
      def fetch_orders(self) -> List[OrderRecord]: ...
  ```
- **Paper Simulator**: Default implementation of `ExecutionBroker`. Models slippage, bid-ask spreads, and transaction costs.
- **Zerodha Adapter Boundary**: `ZerodhaExecutionBroker` implements `ExecutionBroker`. Live order submission is hard-locked behind the triple safety fuses. Transitioning to Zerodha requires flipping configuration flags without modifying strategy or risk logic.

## 4. Cloud Infrastructure & Operational Resilience

- **Runtime Environment**: Docker Compose on a single cloud VPS or dedicated container instance.
- **Service Composition**:
  - `web`: FastAPI / Uvicorn ASGI server hosting the authenticated API and dashboard.
  - `stream`: Dedicated daemon process ingesting Upstox WebSocket ticks and aggregating 1s/1m bars.
  - `position_manager`: Dedicated high-frequency 1-second position monitoring process.
  - `worker` & `beat`: Celery processes handling gap backfills, EOD calendar sync, and bhavcopy ingestion.
  - `postgres`: PostgreSQL 17 with automated daily WAL backups.
  - `redis`: Redis 8 for low-latency pub/sub telemetry (`nivesh:positions:live`) and cache.
- **Health Checks & Telemetry**:
  - HTTP `/api/health` probes feed freshness (heartbeat $< 5\text{s}$ during market hours).
  - Automated alerting webhook for feed drops, risk limit breaches, or reconciliation errors.
  - Graceful restart with automatic position state reconciliation from PostgreSQL.
